# web论文写作：Chat 写作入口

本文中的 Drive 路线适用于已配置且选择该渠道的项目。无 Drive 的项目可继续本地工作，并按[文件交付策略](file-delivery-policy.md)使用实际可用且获准的 MCP 文件接收。`drive_links_only` 只在连接明确返回该设置时生效。

本入口用于普通 ChatGPT 写作聊天。按所选 App/Tunnel 的真实能力，使用 Codex 交接的材料完成论文正文、图源调整、排版、审阅和已获准的交付。

## 本轮动笔前

基稿以用户指定或工程当前的可编辑源为依据。已有项目绑定时，定向读取本次段落、图或批注及它依赖的材料。调用 `paper_project_context` 时，如果返回了 `continuation`，用它核对已有 `PROJECT_STATE.json` 登记的版本、源路径及哈希实况。兼容未返回该字段的连接，直接读取现有状态与候选记录。写作以工作源为准，已交付审阅稿、作者认可稿、外部源包各沿实际身份取件。哈希相符说明登记的文件字节得到核对，作者接受和后续版本需要各自证据。

登记源变更、两种语言的科学身份冲突或作者决定不清时，核对当前归档、作者批注和明确指定的基稿。只暂停依赖歧义的合并或事实修订，继续已能完成的具体写作和检查。不得从文件日期、版本大小或历史链接猜测。作者用其他论文展示版式或文风时，沿用当前项目身份。

使用[论文表达与编辑验收](editorial-review.md)中本次相关部分。收到“继续”时，恢复同一稿件的最近未完成步骤，带上作者已接受的写法或图件选择。用户明确要求实改时交付实际成稿、具体位置和可核验差异。范围内可逆工作直接推进，重大科学取舍或缺少授权的动作按现有入口处理。

## 普通 Chat 的项目与写作风格

每篇论文优先使用一个专用普通 ChatGPT 聊天和一个目标 App/Tunnel。首次选择该 App 后，通过其实际工具确认真实 `project_id`、根目录与授权范围，并把本轮范围与既有材料衔接。用户首轮明确给出 `tunnel_id` 时，对照宿主可见的连接信息或可信 App–隧道映射核验。宿主未显示隧道身份且无可信映射时，分别报告已核的项目与未核的指定隧道。发现映射冲突时暂停依赖该连接的项目操作，给出同一连接的恢复步骤。后续同一聊天沿用已确认的绑定，用户可直接说“继续润色”“改图2”或“展示修订版”，无需重复 `@` 或重述项目 ID；实际工具参数仍携带真实 `project_id` 及要求的配置身份。

每次起草、续写、翻译、润色或按批注返修前，都读取并应用本包的[反防御写作原文](anti-defensive-writing.md)。后续回合继续使用同一份规则，按原文的检查流程整理本轮文字，直接向用户交付写作结果，无需复诵加载状态。纯取件、构建状态查询和文件交付按各自定向入口执行。

规则只作用于 Chat 的写作表达。项目事实、引用证据、作者决定、真实执行结果和权限继续按本工作流核对。保留证据要求的不确定性、研究范围、方法条件、负面结果和必要限定。Codex 材料入口沿用科研证据与本机执行规则。

该原文随 web论文写作包发布，读取路径为当前技能目录下的 `references/anti-defensive-writing.md`。Chat 从当前包读取此文件。若宿主没有提供该文件，报告本包缺项并恢复当前包的规则入口，不能将生成稿标记为已应用该规则。当前 Chat 丢失项目工具时，重新选择原 App，核其 `paper_runtime_status`，再用读回的真实 `project_id` 接续。报告具体缺口与已完成部分，给出同一连接的恢复步骤。

当前修订已有相应 PDF 和已核 Drive 链接时，直接按下文的展示格式回复。需要制作新对照稿时，按[轻量文字对照](review-confirmation.md)生成标记 TeX 和一份审阅 PDF。按原模板编译，Drive 只展示该 PDF；作者确认后按本轮要求保存修订。长期逐项审批可使用已启用的结构化审阅。

先区分纯取件和写作。已有可信绑定时，用户仅要指定版本/语言/图号的内容，按 [精确目标取件](indexed-targets.md)直接读取；不先做宽泛runtime、项目inventory、目录扫描或Drive search，不触发写作、构建或发布。只核必要的本次目标身份；明确未启用的旧工程缺口。

建立新绑定或需要全面写作上下文时，先用 `paper_runtime_status` 核连接和真实授权项目，再调用 `paper_capabilities` 与 `paper_project_context`。按 [统一能力发现](capability-discovery.md) 区分可用、未配置、无权限和不支持的能力以及 Host/Provider/Native 路由。旧实例使用实际 `runtime_status`、项目发现、`read_files`，不猜工具名/Schema/项目ID，不把某个项目连接固定为旧工具版本。分批读实际 PROJECT/HANDOFF/状态，按 [Codex交接提示](chat-handoff-template.md) 核当前稿、材料简介和未决项。`paper_research_state` 实际存在时用于验证状态引用；工具缺失或未配置时通过授权读取定位权威状态，不扩权限创建新状态。根目录或权限不符时停止依赖该连接的写入。

项目选择云规范库或 Drive 镜像时核验其 ACTIVE_LIBRARY.json、manifest、项目目录与真实授权。本地模式读取项目锁定的本地期刊材料和模板。

按 [任务模式](task-modes.md) 选择 FULL_PAPER / SECTION_EDIT / FIGURE_EDIT / REFERENCE_EDIT / PDF_REVIEW / ANNOTATED_PDF_REVISION / VERSION_COMPARE。仅局部润色不强制新建完整投稿包。目标 Information Fusion 等期刊需核对应稿型、阶段和官方当前要求，不将团队默认模板视为官方认证。

按现有 [科学证据](scientific-evidence.md)、[期刊及 Drive](venue-and-drive.md) 的事实和检索规则执行。当前 unified 项目契约优先于这些参考中旧入口命名；web论文写作接管角色路由。规范不改变研究事实，参考案例不当本项目方法证据。

已授权编辑使用实际可用的 `paper_edit_files` 或旧接口 `edit_project_files`，按真实Schema精确替换/创建，读回核hash与numeric revision。图源依任务使用真实数据、原生PPTX、SVG/TikZ；保持可编辑要求，定位生成器/实际数据/input_manifest，不能只修改导出PNG。构建以实际context或provider发现的Schema、输入SHA及输出根为准；旧配方不匹配当前源稿时报告具体缺口，缺工具或入口禁用时不假装执行。

论文正文、可编辑图源、生成脚本及构建输入以当前已核 `PaperWriting` 工程为唯一后续写作源。改图先定位项目中的源文件，原生 PPTX 使用实际可用的 `paper_pptx_inspect`、`paper_pptx_edit`，脚本图使用 `paper_figure_build`。按实际 Schema 核源 SHA，并从该本地源构建 PDF/PNG、执行本机检查和记录输出 SHA。Chat 查看图件或页预览时沿已核 Drive ID 读取。`paper_pptx_edit(action="export")` 是本地 PPTX 渲染操作，按其独立 Schema 使用。

PPTX 制作按任务选择一条执行路线。用户明确选择本地或云端时沿用该选择。修改工程已有图源、需要用户用 Windows PowerPoint 接着改时，默认由 Chat 调用所选项目连接的本地项目工具。参考图复刻或当前云端工具更适合所需对象与版式时，可以在云端制作，再通过项目 Drive 回收到本地。先核对相应工具、素材与已获授权的传输范围；用一句话说明本轮选择。只有两条路线的取舍会实质影响复刻效果、原生可编辑性，或所需素材、传输入口与授权确实缺失时，询问一个具体选择或操作。同一制作任务默认生成所选路线的结果。

本地路线按下方调用顺序执行。云端路线允许先把临时环境中的原始可编辑 PPTX 上传到本项目已绑定的 Drive 目录作为桥接文件，再按其真实文件 ID 回收到 `PaperWriting` 获准的新候选路径。上传保留 Office MIME，记录原始字节大小和 SHA；回收核对项目目录、远端文件身份、实际下载字节与本地落盘 SHA。随后从本地候选生成或核对 PDF/PNG，完成该图交付所需预览。桥接上传属于图源交接，正式论文发布仍按作者指令执行。项目没有 Drive 时优先完成本地路线；已有可用且获准的原件直传入口时，也可按实际接收能力回收云端原件。

两条路线都在可编辑原件实际进入 `PaperWriting` 后记录工程交接完成。候选记录关联图号、语言、图版本、所选路线、源路径与 SHA、变体角色、构建产物及对应 Drive ID，沿项目已启用的精确索引或明确路径取件。回收或检查存在缺项时，记录已保存位置与待完成步骤并继续可执行的回收。图件候选的采纳依作者确认登记到论文修订。

本地 PPTX 图件按以下调用顺序完成工程写回。先读取所选项目实际工具 Schema、可编辑源和输入身份。使用 `paper_pptx_edit(action="create", deck=...)` 新建原生对象，或对已有工程 PPTX 使用 `action="edit"`、真实 `pptx_path`、`expected_revision` 及所需 `program`/`commands`。涉及图片、复杂对象或已有素材时，使用该工具已支持的项目输入和对象操作；先按实际能力核对所需素材路径。

`paper_pptx_edit` 返回 `build_id` 后，用 `paper_build_status` 查询同一任务，取得 `completed` 和实际工件清单。该输出位于工程构建区。随后对清单中的 PPTX 调用 `paper_build_artifact(action="copy_to_candidate", build_id=..., path=<实际工件路径>, destination=<获准的新候选相对路径>)`，把可编辑原件保存到当前 `PaperWriting`。该动作只创建新目标，使用复制回执中的路径、SHA、大小和来源任务核对落盘身份，再用该候选路径执行 `paper_pptx_inspect`。需要继续改同一工作候选时，读取其最新源 SHA，再编辑并保存本轮输出，按实际工具的并发与目标存在检查处理。

从落盘源生成的 PDF/PNG 同样按实际工件清单登记。图源、预览及源 SHA 的对应关系确认后，同步本轮需要的 Drive 审阅文件；云端路线已有的桥接 PPTX 按原 ID 关联。任务返回 `completed`、聊天附件链接或临时路径时，继续完成上述工程写回步骤，直至能提供真实的项目源路径与回执。同一轮制作“原图加可编辑页”的合成版和单页可编辑版时，两份文件分别登记角色、页数、路径与 SHA，并关联到同一图件候选批次。图件候选与论文修订按作者确认采纳，无须因保存这两个变体自动新建论文版本。

云端原件回收优先使用本项目实际可用的按 Drive 文件 ID 导入能力；接收端可读取的真实上传 URI 或本地 Codex 回收也是可选入口。`/mnt/data/...` 是该 Chat 环境的临时路径，WSL 与隧道对它的访问能力须按实际工具结果确认。Drive 已上传时沿已记录的文件 ID 继续回收，完成后给用户真实项目路径。缺少原始字节或接收入口时说明具体缺项，工程交接保持待回收。

当前连接提供 `paper_pptx_edit(action="import_drive")` 时，按其实际 Schema 传入 `drive_source={file_id, project_folder_id?, parent_id?, expected_sha256?, expected_bytes?}`、项目获准的 `destination` 与唯一 `request_id`。导入工具可根据 `file_id` 只读推导父链，核对其属于原 Publisher 的直属项目目录；传入预期 `project_folder_id` 或 `parent_id` 时必须与实际结果一致。初次上传的 `parent_folder_id` 从本项目已知审阅回执取得项目目录或既有候选子目录，并保持在该项目可接收范围内。先用 `dry_run=true` 读回项目目录校验与原件指纹，核对本轮已获授权范围后，以 `dry_run=false, authorized=true` 应用同一导入计划。使用实际响应核对本地路径、SHA、大小和待完成操作，按工具返回的任务 ID 查询实际完成状态。源文件、远端指纹或目的路径有变化时重新读取计划。

云端上传使用当前可用的 Drive `upload_file`，传入宿主实际可读取的原件 `file_uri`、原文件名、`application/vnd.openxmlformats-officedocument.presentationml.presentation` 和本项目真实 `parent_folder_id`。记录上传返回的文件 ID 后再调用上述回收入口。来源文件只在另一个宿主中可见时，取得当前上传宿主可读取的原始文件或已有获准传输入口后继续；图源桥接沿用本轮既有授权。

PPTX 图源的 Drive 副本保留 `.pptx` 文件及其 Office MIME 类型，上传后核对远端大小、SHA 和本地源身份。用户明确要求 Google Slides 时，另行记录转换稿与本地 PPTX 的对应关系及实际核验范围。Drive 展示文件和批注按已知 ID 回收至同一项目。


文字对照审阅保留当前稿号，受控生成审阅 TeX 及 PDF。用户要求应用修改时，持续编辑当前manuscript/workdir，不自动升新论文版本；项目启用受管版本时改按[受管版本](managed-versions.md)：只在 draft 版本内编辑（working 双语主稿与 `working/deps` 支持文件；`.bib`、新增 `\input` 文件和增删图表经依赖候选与结构声明进入新 revision），已发布版本先 restore。构建前使用实际可用的 `paper_build_plan` 核当前主稿 SHA、递归输入与预期快照；未配置目标时报告缺口，不把旧稿配方当当前入口。获准且实际可用的构建工具生成独立输出并保留任务/输入关联；`paper_manuscript_build`存在时沿用其bNNN/rb约定，旧接口不假设相同命名。指定引擎、固定字体兼容 hook 和搜索目录由可信项目配置注入，不向 ChatGPT开放任意命令或任意 TeX hook。旧PDF标历史。完整论文任务交实际PDF，真实阻塞则交已完成源稿及缺口；图件任务交编辑源和实际预览，只读PDF审查不擅自构建。静态、编译、视觉、Drive上传和用户下载分别验收。

批注任务先按 [annotated-pdf](annotated-pdf.md) 匹配被批注真实版本和哈希，在新候选稿处理 resolved / needs-author，不按坐标猜旧稿身份。该旧参考的发布步骤仅在本轮已有版本/云端发布授权时执行，局部修正本身不产生发布授权。

默认展示路径覆盖论文 PDF、图件、PPTX 和页预览。需要 Chat 看到本地文件时，先复用已核项目 Drive 链接；需要上传时核实当前项目实际支持的单文件展示或原 Publisher 入口，再按实际回执给出链接。Chat 视觉审阅通过 Drive 连接器按已核 ID 查看所需文件或页面。本机继续构建、渲染、检查和返回文字/元数据。展示不额外新建正式论文版。

`drive_links_only` 模式的展示和视觉审阅不使用项目连接 `image`、工件 `export`、ResourceLink/resource、预览 widget、二进制分片或聊天附件。附件请求按[文件交付策略](file-delivery-policy.md)处理。Drive 失败时记录该目标的具体缺口，继续已授权修复。无 Drive 时继续本机工作，并按[文件交付策略](file-delivery-policy.md)报告本机文件和可用链接。

## Drive 稿件展示格式

首行用一句话交代本次稿件的版本和状态。版本归档记录和对应标记稿的正式发布回执齐备时，可写“{版本} 已归档，全文修订标记版已发布。”仅供审阅时写“{版本} 中文修订标记版已可审阅。”沿用实际稿号，章节稿写明章名。收到“展示”时直接取回已有交付链接。

默认每份 PDF 占一段。第一行就是可点击的 Google Drive 文件直达链接，链接文字按“版本＋语言＋范围＋稿件类型（实际页数）”书写。下一行用一句话说清读者会看到什么。四种稿件均有时，按下列顺序展示；用各自交付回执中的 URL 和各自 PDF 的页数替换模板中的占位符。

```markdown
{版本} 已归档，全文修订标记版已发布。

[{版本} 中文全文修订标记版（{页数} 页）](https://drive.google.com/file/d/{中文标记稿文件ID}/view)
{本轮修改了什么，以及上一版批注在何处保留。}

[{版本} 英文全文修订标记版（{页数} 页）](https://drive.google.com/file/d/{英文标记稿文件ID}/view)
{英文稿中的可视修订痕迹。}

[{版本} 英文全文净稿（{页数} 页）](https://drive.google.com/file/d/{英文净稿文件ID}/view)
{简述英文净稿的阅读范围及已纳入的修改。}

[{版本} 中文全文净稿（{页数} 页）](https://drive.google.com/file/d/{中文净稿文件ID}/view)
{简述中文净稿的阅读范围及已纳入的修改。}
```

只列本轮所需且有真实文件链接的稿件。单份沿用同一格式；用户明确要求“只给链接”时，只回复所需文件的直达链接。若用户点名要中文净稿而回执缺失，用一句“中文全文净稿暂无已核验的 Drive 链接”说明，保留其他可用稿件。页数未知就省略页数。使用普通可点击的链接，无须先导入 Chat 文件库或打开侧栏。

## Chat 正文展示与公式可读性（强制，2026-11-09 Chat 端增补）

当用户要求“展示正文”“显示方法/实验设置”“给我看论文内容”“中文对照”“逐段审稿”或要求阅读、批注论文中的数学表达时，**必须在聊天消息里直接提供可阅读的正文和正常渲染的公式**，不能只交付文件路径、附件、源代码或下载链接。展示范围遵循用户请求；既不擅自缩写关键推导，也不因原文件是 TeX/Markdown 就逐字输出排版源码。

1. **正文排版**：用正常 Markdown 标题、自然段、少量必要的表格呈现原有章节结构。公式与解释就近出现。禁止把整篇正文仅塞入不会渲染数学的 `WritingBlock`、`CodeBlock`、三反引号或纯文本标签；即使另提供可复制/编辑稿件，也必须在聊天中保留直接可读的数学展示。原始可编辑 TeX/MD 文件仍作为独立交付，不改变其源格式。
2. **数学公式**：行内公式使用 `\(...\)`，独立公式使用 `\[...\]`，多行推导在独立数学块内使用适当的 `aligned` 等 LaTeX 数学环境。优先采用客户端能原生排版的数学表示，而不是渲染为反斜杠字符的源码、代码截图或普通文字。示例：行内 `\(S_{10}\)`；独立展示 `\[S_{10}=\frac{1}{N_+}\sum_{i=1}^{N_+}\mathbf{1}\{|e_i|\le10\,\mathrm{m}\}.\]`。保留分式、上下标、向量、求和、矩阵、单位与变量解释；不要将公式简化成易产生歧义的一行字符。
3. **TeX 到聊天的转换**：从项目中的 `\begin{equation}...\end{equation}`、`align` 等源码提取数学内容，在聊天中转换为真正可渲染的独立公式；把 `\eqref{...}` 换为对应编号的可读引用。保留原式及编号关系，不擅自改符号、改量纲、重推导或补造不存在的公式。必要时在公式下方说明符号含义。
4. **WritingBlock 与公式冲突时**：若写作块无法可靠显示数学，可用它提供一份可复制的纯文本草稿，但**不能作为唯一可阅读的正文**；在写作块外按原文顺序展示全部请求范围内的数学公式和相关段落。若任务是展示已写正文而非另写新稿，优先直接展示排版后的正文，不强制用写作块包裹。
5. **视觉验收**：交付前目视或依据实际渲染检查公式是否成为数学排版，特别检查 `\frac`、`\sum`、`\int`、上下标、希腊字母、单位、矩阵、编号和断行。若当前界面无法渲染某个复杂公式，明确指出并选择实际受支持的数学或已经构建的 PDF/图片预览途径；不能声称原样 LaTeX 源码已经可读或公式已经渲染。
6. **中英文对照**：中文与英文逐小节对应时沿用同一公式、编号、符号与单位，仅翻译解释文字，不产生两套不一致的科学定义。长文允许按章节分段展示，但不能只给目录或摘要来替代用户指定的完整正文。

这是一条 **Chat 端交互展示规范**，不改变论文事实来源、投稿模板、项目的受控 TeX 源、版本授权或实验结果。
