# 文字对照审阅与确认稿

用户要求“展示修订版”“给我看看改动”时，先按当前版本、语言和范围取已有对照 PDF；所选成品已有 Drive 回执时，按[Drive 稿件展示格式](chat-writing.md#drive-稿件展示格式)直接给链接。需要生成对照稿时，默认执行轻量文字对照。已有两份 TeX 就按指定版本和语言定向读取，核对输入哈希。只有原稿和用户给出的改写时，直接在内存中比较指定段落并生成标记 TeX；候选文本可从标准输入传入，不需另存一份论文。生成一份带修订标记的 TeX，沿用原工程的模板、图、参考文献和受控编译入口，编译为一份审阅 PDF。删除文字使用红色删除线，新增文字使用蓝色下划线；用户另有指定时沿其高亮或其他标记样式。文字标记应支持中文断行，公式、引用和特殊命令需核实际编译效果。

审阅沿用当前论文版本号。产物只需标记 TeX、审阅 PDF 以及正常构建所需的临时工件。输入路径与哈希、PDF 哈希和 Drive 文件 ID 记录在现有构建或交付回执中即可。正文对照审阅无需创建论文版本、子版本、提案、逐项决定实体或另建索引，无需复制整套工程、导出后转存回写或冻结中间论文版本。项目读写权限和受信的 TeX 编译范围仍由当前工具配置核对。

Codex 在本机按现有受控工具生成对照稿；管理工程提供 `management.paper_tex_redline` 时，可从两份明确源文件生成指定输出，分章模式沿用原主稿并只替换指名的文字输入。底层 `latexdiff` 与中文标记支持先在原工具链核验。Chat 按当前可见工具的真实 Schema 精确读取两稿、创建带标记 TeX 并提交构建；已有比较工具可辅助取得差异。允许文字审阅的实例可在已登记 `main_zh.tex` 的同目录使用 `main_zh.review.tex`，沿用 `paper_build_plan`、`paper_tex_build_submit`；生产尚未启用这个轻量入口时由本地 Codex 接续。缺少该入口时报告具体缺口并交本地 Codex 接续，不为此自动升级受管版本。分章稿按指名的章文件及其直接依赖处理；定位缺失时报告缺项，定向取件继续按既有索引执行。

项目选用 Drive 时，从 Runner 的本次构建产物调用已配置的原生单文件 Publisher，提供实际文件链接，并核服务端 SHA-256、大小、父目录与可读状态。Runner 执行本机检查和渲染，Chat 通过已核 Drive PDF 或页预览 ID 完成所需视觉审阅。附件请求按[文件交付策略](file-delivery-policy.md)处理。

已有当前受管普通 TeX 目标的成功净稿构建时，也可直接用 `paper_publish_to_drive(review_pdf={build_id, sha256, language, project_folder_id, parent_id})` 交付该份净稿供审阅。选择实际完成的构建 ID 与其主 PDF 的准确 SHA，核对它对应本轮版本/修订及已绑定的语言、项目目录和展示子目录。复用该次净稿 PDF，展示沿用实际稿号；作者要求对照时才另行生成标记稿，正式版本发布沿其明确指令执行。Chat 仅返回核验过的 Drive 直达链接并按[文件交付策略](file-delivery-policy.md)读取，不在 Chat 中实体化净稿。

Chat 的 `paper_publish_to_drive` 若列出 `review_pdf`，传入这次审阅构建 ID、PDF 哈希、语言和已绑定的展示目录 ID，直接返回单份 PDF 链接。该调用只使用 `review_pdf`。旧工具只列出 `version` 时，可由本地执行同一交付。本地 `management.paper_review_display` 可指定已有构建 ID 或审阅 PDF 和绑定目标目录，直接展示外置构建 PDF，沿用其回执 ID 读取批注，无需中转或重复编译。按项目当前发布器能力选用最小上传范围；若可用发布动作只接受完整版本包，先报告这个具体能力缺口。正式归档和整包 Publisher 不构成文字对照的前置步骤。用户在 Drive 批注时，按本次展示回执的文件 ID 读取评论和回复，关联语言、页码、原句或图号；无法定位的意见保留待确认。批注窗口的“已解决”不代替作者接受改动。

作者确认意见后，应用本轮已授权保留的内容。只有用户要求保存工作修订或正式发布时，才调用相应的版本管理入口。工作修订按两段整数递增，例如 `1.1 → 1.2`；用户明确升大版本才采用 `1.2 → 2.1`。正式发布另核本轮指令，检查当前正文、图和参考文献与成功构建一致。正文、图或参考文献变化后重新构建受影响语言；旧 PDF 重新登记或上传 Drive 均不能替代正式发布核验。历史清理由用户单独要求。

换图审阅时划去原图并展示新图，标明同一图号、语言和候选身份。用户需要长期逐项记录、多轮审批或严格确认链，且项目已启用 `paper_review_proposal` 时，再用 `propose`、`render`、`get`、`decide`、`apply`。提案、渲染和批注维持当前稿号；待确认条目、单纯评论及“请再调整”保留待确认状态。确认选择后再应用。原排版位置不明确时，可在对照页说明或由用户指定页码和区域。结构化审阅入口与轻量文字对照按实际任务选择。

Codex 维护端按交接 ID 或 manifest SHA 定向登记新材料。Chat 用 `paper_material_get`，或已启用的 `paper_read_files` 兼容路径 `paper-handoff://交接ID`、`paper-handoff://sha256/完整SHA`、`paper-handoff://~`。首次为旧项目建立索引是单独的管理操作。日常命中只核所选包及直接前驱身份，缺项就报告缺项。具名图、表、图源在角色后追加 `/key/名称`，例如 `paper-index://paper/1.2/zh/figure_pdf/key/S1`；普通数字图号继续用 `/figure_pdf/2`。Drive 按已有展示回执的文件 ID 读取。

两种语言沿用各自受信的构建入口，单语言审阅按用户指定语言构建。长稿评阅使用 `paper_pdf_review` 的 `pages` 或含 `start`、`end` 的 `page_ranges`，页码从 1 起，区间含首尾。一次最多渲染 60 页，可点名第 61 页以后的页面。旧聊天工具只显示 `pdf_path` 时，可使用同一已登记 PDF 的 `#page=62` 片段指定单页并核对回执的 `selected_pages`。交代文档总页数、实际渲染页和已看过的页面；页面内容检查包含删除线、下划线、颜色、中文断行和引文。
